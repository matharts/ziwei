# 跨语言领域合同

本合同规定所有排盘实现必须保持一致的 V1 领域行为。它不要求实现复刻 Rust 类型、内存布局、错误类、方法名或宿主生命周期。当前项目规则的唯一来源是 [`CONTEXT.md`](../../CONTEXT.md) 与其引用的已确认决策；本文件划定合同范围并链接回规则来源，不复制第二份排盘规则。

Rust 核心、现有 Node 原生绑定和 Wasm 包描述迁移期间的实现状态，不是领域行为的 oracle。任何实现或批量生成的输出都不能单独证明预期结果正确。跨语言验收使用带有规则依据、独立推导说明和稳定标识的[共享用例](../../conformance/README.md)。

## 输入语义

- 支持两种规范输入：`Birth` 提供性别、数字年份、归一化出生月日及时辰；`Parameters` 提供性别、有效六十甲子年柱、归一化出生月、给定紫微地支及时辰。两种输入必须归一到同一组本命事实。
- 年份允许负数、零和实现所声明整数范围内的值；不得经无符号转换、截断或宿主日期类型换算。数字年份及出生日期不是公历日期有效性承诺。
- 月份范围为 1 至 12，出生日范围为 1 至 30。引擎不校验某个具体月份实际有几日，也不承担历法换算、闰月辨识、晚子时、时区或真太阳时。
- 六十甲子年柱只接受阴阳相配的天干与地支。`Parameters` 的紫微地支是调用方给定的领域值，不从输入重新安紫微。
- 输入错误必须在计算前被识别，不能静默修正、猜测、截断或替换为默认值。具体范围与字段来源见 [`CONTEXT.md`「输入与校验」](../../CONTEXT.md#输入与校验)。

## 本命事实与计算

- 每份成功结果表示一个不可变本命盘；两种规范输入遵循相同规则，不因输入入口改变排盘事实。
- 本命盘有十二个实际宫位，稳定顺序为寅、卯、辰、巳、午、未、申、酉、戌、亥、子、丑。十二种宫职身份各出现一次；空宫及多星同宫均有效。
- 十八种星曜身份各出现一次，且每颗星恰在一个宫位。顺序、星系与星名身份以 [`CONTEXT.md`「星曜与四化」](../../CONTEXT.md#星曜与四化)为准；显示文字不得用作规则键。
- 命宫、身宫、来因宫、紫微宫均须唯一且彼此一致；来因宫由固定生年干映射决定，不得通过扫描宫干反推。
- 五行局、宫干、生年四化和自化均为本命事实。每一宫固定产生禄、权、科、忌四项宫位四化关系；同宫关系保留，不能把它改作连续飞化路径。
- `Birth` 依已确认的五行局与出生日规则定位紫微；`Parameters` 使用输入给定的紫微地支。固定定位规则见 [`CONTEXT.md`「核心不变量」](../../CONTEXT.md#核心不变量)及 [V1 决策 D-214～D-224](v1-decision-map.md)。

## 查询、期间与缺失值

- 领域身份查询以宫职、地支、星曜或化象身份定位；简繁名称和简称仅用于展示，不能作为规则选择依据。
- 多项结果的顺序必须稳定。宫位、星曜、四化、对宫、三方、四正及来源查询的具体顺序见 [`adapter-contract.md`「输出与顺序」](adapter-contract.md#输出与顺序)及对应的已确认 V1 规则。
- 大限与流年按请求按需计算，只为相应期间分配宫职及年龄／年份摘要；期间结果不得修改或覆盖本命盘的星曜、宫干、四化或宫职事实。
- `Parameters` 不含数字年份与出生日。所有实现必须保留这种缺失：不得用零、空字符串或推造日期补值。对于缺少出生年份时不可得的数字年份摘要，使用明确缺失值。
- 合法身份查询返回由 V1 合同决定的唯一对象、集合或边界空值；不能用结果的真值缺席错误替代领域语义。所有接口名与线缆表示由各实现自己的宿主合同决定。

## 错误语义

- 失败必须对应已确认的输入值域或查询边界；错误保留机器可区分的语义类别及导致失败的相关载荷。
- Rust 错误变体、TypeScript 异常类型、字符串错误码、消息语言及 JSON 结构均属于实现／宿主适配合同，不能反向定义领域行为。任何绑定都不能通过解析展示文本或依赖语言运行时的枚举布局还原错误身份。
- 具体输入字段和已确认边界错误见 [`CONTEXT.md`「输入与校验」](../../CONTEXT.md#输入与校验)及 [`adapter-contract.md`「错误合同」](adapter-contract.md#错误合同)。实现新增或改变失败条件，须先更新项目规则与决策记录。

## 一致性要求

1. 新增或修改规则时，先更新权威规则及决策沿革，再同步本合同链接或范围；不在多处复制同一张完整规则表。
2. 新实现必须通过共享 conformance cases，并各自保留必要的单元测试、宿主合同与发布验收。
3. 共享 case 的预期事实须独立推导，逐项注明来源和适用口径。跨入口对照、Rust 输出、TypeScript 输出和实现生成的快照只算一致性证据。
4. 用例覆盖状态按领域能力与各实现分别登记；有少量手算锚点不等于整个 V1 领域合同已经完整覆盖。

# 按需增加语言原生实现的重构计划

日期：2026-09-19。

状态：本地实施中。2026-09-28 已按用户决定以 TypeScript 独立实现直接替换 `@matharts/ziwei`，并移除旧 Rust Node 绑定与 Wasm 源工程、包、任务和 CI。Node 公开测试、干净安装消费、类型合同及 Chromium／Firefox／WebKit 页面与 module Worker 测试已在本地通过；远端 CI、发布与移动设备实测尚无结果。共享 conformance 用例仍需逐步扩充，实际证据边界见[实现状态表](implementations.md)。以下阶段描述保留迁移设计与验收要求，不能替代当前验证记录。

## 目标与边界

将项目从“唯一 Rust 领域实现、其他语言通过绑定使用”演进为“统一领域规格与验收用例、各语言独立实现”。Rust 保留为正式实现之一；新语言消费端不依赖 Rust、FFI、Wasm 或远程排盘服务。

每种语言可采用自然的类型、命名、错误表达和对象管理方式，但必须遵循相同的排盘语义。只在真实需求出现时增加实现，不创建未来语言的占位包，不要求一次实现所有语言。

本轮架构迁移不增加历法换算、闰月、晚子时、时区、真太阳时、解释断语、连续飞化或计算追踪，不修改既定排盘规则。Rust 核心保留为独立实现；纯 TypeScript 已接管 `@matharts/ziwei`，同一入口供 Node 与浏览器使用。旧 Node 绑定与 Wasm 交付路线已退出源工程。移动原生绑定暂停状态不因本计划自动解除。

## 计划制定时的基础与本次处理

| 当前基础 | 重构处理 |
| --- | --- |
| `crates/ziwei` 承载完整 Rust 领域实现 | 保留位置、公开 API 和现有测试，接入公共语义验收 |
| `bindings/node` 调用 Rust | 已移除绑定源码与原生产物流程；Rust 领域核心仍独立保留 |
| `bindings/wasm`、`packages/ziwei-wasm` 曾在仓库中 | 已移除 Wasm 专属源码、包、任务和 CI |
| `packages/ziwei` 曾为 Node 原生消费包 | 保持 `@matharts/ziwei` 包身份和根入口，内部改为纯 TypeScript 并增加浏览器消费验收 |
| `packages/ziwei-shared` 曾共享 JavaScript 输入、错误与只读投影 | 纯 TypeScript 包独立实现后已删除；不再承担适配职责，也不是跨语言规则核心 |
| `CONTEXT.md`、V1 决策表、适配合同记载领域语义 | 明确各文档职责，提取语言无关合同，避免复制成多份权威文本 |
| Rust 固定命例已有独立手算预期 | 提取为语言无关数据，保留来源和推导，不由引擎输出重写预期 |

需要在阶段一明确修订 D-260 及现行架构中“不引入第二套领域实现”“唯一可以执行排盘规则的包”等全局限制，并记录对 D-263 Node 原生分发与 D-267 浏览器交付路线的修订。Rust 包内部职责在过渡期不变；Node 绑定单向依赖关系随绑定退役结束。历史决策保留，以新决策说明被修订的具体范围，不将旧决策全部删除。

## 阶段一：明确规格权威与实现边界

**交付物**：新增语言无关领域合同与实现状态表；同步 `CONTEXT.md`、V1 决策表、Rust 架构文档、适配合同及必要的 README／AGENTS 导航。

职责划分：`CONTEXT.md` 负责术语、范围和不变量；`domain-contract.md` 负责输入值域、计算行为、查询顺序、缺失值和领域失败语义；V1 决策表负责决策沿革；各语言设计文档负责具体 API 和宿主约定。相同规范内容通过链接引用。

领域合同至少覆盖：

- 两类输入、有效六十甲子、负年与零年、数值范围及归一化行为。
- 十二宫、十八星、五行局、定位、生年四化、宫干四化及自化。
- 大限、流年按需生成，期间宫职不得覆盖本命事实。
- 输出顺序、多重关系、空集合、缺失数字年份及扩宽后的年度输出。
- 只读事实、错误类别与语义载荷，领域身份与展示名称的区分。

单独保留 Rust 借用、内联存储、JavaScript 输入捕获等实现／宿主合同。Node 原生句柄与 GC、Wasm `dispose()` 仅属于待退役实现，不进入 TypeScript 或公共规格。公共规格不强迫所有语言使用 Rust 类型、JS 错误类或显式释放。

**完成条件**：不存在仍然禁止独立实现的现行全局约束；领域规则没有变化；现有公开 API 合同没有被意外放宽。纯文档检查差异、相对链接和指令一致性，不跑无关构建。

## 阶段二：建立语言无关验收数据

**交付物**：`conformance/` 的格式定义、固定命例、来源说明与覆盖清单。

从 `crates/ziwei/tests/fixtures.rs` 及其来源文档提取可共享的已确认用例。按建盘、只读查询、四化、期间、边界及失败场景组织；每条用例记录稳定 ID、规格版本、输入、操作、预期结果、依据与推导说明。

建议采用 JSON 作为测试交换格式；确切字段在本阶段设计。该格式仅用于验收，不自动成为公共序列化 API，也不强制各语言的 `toJSON` 与它一致。使用稳定身份表示星曜与宫职，不以中文名称或 Rust enum 内存布局充当标识。

固定以下比较规则：

- 有语义的数组顺序必须保留；对象键顺序不参与比较。
- 缺失值、空集合与零值必须区分，禁止自动排序掩盖顺序错误。
- 领域错误比较类别与语义载荷，不比较语言特有异常类或完整错误文案。
- JavaScript 的 `NaN`、getter、错误输入类型等宿主专有测试留在语言侧，不硬塞进公共 JSON 命例。
- 检查整数精度与范围，尤其是出生年边界和超出 `i32` 的合法年度输出。

**完成条件**：每个合同条款能追溯到测试或明确的验收方式；数据格式错误、未知操作、重复 ID 和无依据预期会失败。保留现有手算来源及“未经外部专家审定”的证据边界。不能把 Rust 输出批量存为正确答案。

## 阶段三：用 Rust 验证公共验收机制

**交付物**：Rust 测试侧的用例读取与执行器，以及根任务入口和 CI 检查。

执行器只把测试输入映射到公开 API、把真实结果投影为测试表示，不重算排盘规则，不修正结果，不进入产品依赖。原有内部单元测试、API 测试和独立手算验证继续保留；迁移后的公共预期只维护一份。

现有 Node 绑定在过渡期保留既有回归检查，不再为待退役绑定扩建公共验收基础设施；它与 Rust 共用算法，不能当作第二个独立实现。Wasm 同样保留既有回归检查。公共用例先验证 Rust，随后成为 TypeScript 的独立验收依据。

**完成条件**：Rust 通过公共合同；故意改变一个星曜位置、数组顺序或错误载荷时，验收能定位到用例 ID 和字段差异。未知能力或未执行用例不能被静默跳过并报告全通过。

验证采用现有 mise 入口；Rust 检查受影响的测试、格式与 Clippy，Node 使用 `check:node` 及相关工具检查。过渡期涉及 Wasm 时仍运行现有 `check:wasm`；删除后同步移除其任务与 CI。新任务的最终名称以实施配置为准，不在计划中声称已有命令。

## 阶段四：实现独立 TypeScript 引擎

**进入条件**：语言与包身份已选定：TypeScript 直接实现 `@matharts/ziwei`，让 Node 和浏览器运行同一套不依赖 Rust、FFI 或 Wasm 的排盘规则。D-273 又确认公开 API 与规则实现从零重写，以 Rust crate 的公开领域能力为清单；原生句柄和旧 Node 门面的对象形状不继承。

TypeScript 独立实现两类建盘、完整本命事实、只读查询、四化与期间计算；Node 和浏览器直接运行同一实现。现有类型、名称和只读投影只有在不引入 Rust／Wasm 依赖且职责合适时复用，不把新规则混入现有适配共享层。

按以下垂直切片推进，每片先通过适用用例，再扩展：

1. 输入和值类型 → 归一化 → 本命基本定位。
2. 星曜及全部本命事实 → 生年四化、自化与宫干四化。
3. 只读关系查询 → 大限、流年及全部边界。
4. 现有 `@matharts/ziwei` 的宿主 API → 类型声明、独立包消费和 Node／浏览器验收。

各语言可以有不同方法名、值类型和错误表达，但不能省略已声明能力的语义。差分测试作为补充；发生分歧回到规格与独立预期判定，不自动以 Rust 为胜方，也不采用多实现多数表决。

**完成条件**：声明范围内的所有公共用例通过，宿主专有测试和独立安装消费通过；构建产物没有排盘所需的 Rust、原生插件或 Wasm 运行依赖。对 TypeScript 在真实 Node 与浏览器中分别验证。完整 V1 支持必须满足完整能力清单，部分实现明确标为实验状态。

## 阶段五：切换交付并退出 Node／Wasm 绑定

TypeScript 达到完整 V1 合同后，让 `@matharts/ziwei` 的 Node 消费端和网页／移动 WebView 消费端使用同一纯 TypeScript 入口。核对现有 `@matharts/ziwei-wasm` 消费者的导入、异步 `initialize` 和 `dispose()` 使用方式，提供明确迁移说明；TypeScript 不继承 Wasm 专属生命周期。比较 API 兼容性、安装方式、包体积与实测表现，不预设性能优势。

Node 与浏览器等价验收、独立安装消费通过后，同一迁移批次删除 `bindings/node`、`bindings/wasm`、`packages/ziwei-wasm`、原生平台包与专属任务、CI，清理 Cargo／pnpm workspace 配置、依赖与锁文件，核对 `packages/ziwei-shared` 是否仍有独立职责，并同步 README、工程指南、架构设计和状态说明。先验证替代入口，再删除旧路径，避免暂时失去消费能力。若涉及基准，先遵循仓库基准规范，明确测量负载、环境和误差；本计划不设未经测量的性能承诺。

持续维护约定：

- 规格版本与语言包版本分开；实现记录所支持的规格及能力，不引入运行时流派或规则选择。
- 规则修正先更新依据与共享用例，再跟踪受影响实现；不悄悄更新预期来容纳回归。
- 公共规格／用例变化触发所有受影响实现的 CI；单语言内部变化只运行适用检查。
- 各实现可独立发版，但未适配的版本必须明确状态，不能宣称符合最新规格。
- 新语言按“需求 → API 小决策 → 独立实现 → 公共及宿主验收 → 支持声明”接入。
- 本地通过、远端 CI、打包和实际发布分别记录。保持当前 private 与发布边界；计划不授权发布。
